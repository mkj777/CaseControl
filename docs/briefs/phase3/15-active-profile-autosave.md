# Brief: always one active profile, autosave, profile dropdown in Lighting (ADR 0001 #40)

Read `docs/briefs/phase2/00-common-rules.md`, ADR 0001 #24, #33, #36, #37, #40, `docs/design-system.md`, then
`crates/cc-config` (profile, store, settings), `crates/cc-engine` (how stored settings and brightness are kept and
applied), `apps/desktop/src-tauri/src` (`profiles.rs`, `commands.rs`, `state.rs`, `tray.rs`, `events.rs`, `lib.rs`,
`build.rs`, capabilities/permissions) and `apps/desktop/src` (`ipc.ts`, `router.ts`, `App.vue`/sidebar,
`pages/ProfilesPage.vue`, the Lighting page and its toolbar, `components/ui`). No new dependencies. Do not launch,
tauri-build or kill the app; nothing that writes to HID or NvAPI.

## Owner decisions

- There is always exactly one active profile (`last_profile` is never empty after start).
- Every change the user makes to what a device shows (device setting via the UI, device brightness) is saved to the
  active profile immediately. No Save / Save as. Coalesce bursts (colour picker drag, slider) so the file is written
  at most every ~300 ms and the last value is always written (also on shutdown).
- New profile: empty (no device settings, no brightness entries), named "Profile N" with the lowest free N >= 1 (name
  comparison case-insensitive, trimmed, as now). It becomes active and is applied (devices fall back per ADR #36:
  readback, else fallback colour, for taken-over devices).
- Duplicate: copies a profile under "<name> copy" (then "<name> copy 2", ...), becomes active.
- Rename any profile (active follows, as now). Delete: not allowed for the last profile (backend refuses, UI button
  disabled with a tooltip); deleting the active one activates the first remaining profile (sorted as the list) and
  applies it.
- Switching profiles applies the chosen one (as `apply_profile_now` does).
- UI: a profile dropdown in the Lighting page toolbar (current name shown; menu lists profiles with the active one
  checked; below a separator: New profile, Duplicate, Rename, Delete for the active profile). Rename inline or in a
  small dialog using existing `components/ui` parts; Delete confirms with `ConfirmDialog`. Follow the design system
  tokens and existing toolbar patterns; keep it compact. Remove the Profiles page, its route and sidebar entry.
- Tray: keep the "Apply profile" submenu (switching); remove "No profiles" handling only if it becomes unreachable.
- Global per-device overrides (hidden, hidden zones, zone sizes) and the fallback colour stay outside profiles.

## Migration at start

- No profiles at all: create "Profile 1" from what the devices currently have stored/shown (same content `save_profile`
  would write now, may be empty), make it active.
- Profiles exist but `last_profile` is empty or names a missing profile: make the first in list order active and apply
  it as start does today.
- Remove commands/permissions that no longer exist (e.g. `save_profile` if unused) from `build.rs`, capabilities and
  `permissions/autogenerated`; add new ones (`create_profile`, `duplicate_profile`, ...) the same way.
