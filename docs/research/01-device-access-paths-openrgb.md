## 1. Access paths on Windows

**a) USB HID (hidapi).** Dependencies: `hidapi-win`, `hidapi-hotplug-win`, `libusb-1.0.27` (https://gitlab.com/api/v4/projects/CalcProgrammer1%2FOpenRGB/repository/tree?path=dependencies). The overwhelming majority of the ~230 `Controllers/*` directories are HID (Corsair alone has 11 directories); vendor families are in the table. `Documentation/USBAccess.md`: "Windows should not need any special setup to access USB devices" and the old WinUSB/Zadig driver "is no longer required, and you need to uninstall the WinUSB driver if you previously installed it" (https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/Documentation/USBAccess.md).

**b) SMBus/I2C.** `i2c_smbus/Windows/` contains only `i2c_smbus_pawnio`, `i2c_smbus_nvapi`, `i2c_smbus_amdadl`. WinRing0 is gone: `SMBusAccess.md` says WinRing0 and InpOut32 "should be removed to avoid warnings by anti-cheat and anti-virus software", and "You must run the application as Administrator in order for PawnIO to be able to access SMBus" (https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/Documentation/SMBusAccess.md). PawnIO was added by merged MR !2833 (2025-05-12, "a secure alternative to WinRing0", signed Pawn modules exposing ioctls) (https://gitlab.com/api/v4/projects/CalcProgrammer1%2FOpenRGB/merge_requests/2833); !2885 ("Switch from WinRing0 to PawnIO") was closed unmerged. PawnIO modules loaded from the exe directory: `SmbusI801.bin`, `SmbusPIIX4.bin` (ports 0/1), `SmbusNCT6793.bin`, `SmbusIntelSkylakeIMC.bin`; a cross-process named mutex (`GLOBAL_SMBUS_MUTEX_NAME`, setting `shared_smbus_access` default true) serializes transfers against other software (https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/i2c_smbus/Windows/i2c_smbus_pawnio.cpp). On Windows, a dialog appears if any I2C bus detector fails: "On Windows, this is usually caused by a failure to load the PawnIO driver... install PawnIO from https://pawnio.eu and run OpenRGB as administrator or as a system service" (https://raw.githubusercontent.com/CalcProgrammer1/OpenRGB/master/DetectionManager.cpp). Claims that a 32-bit WinRing0 build is still shipped come from secondary press: UNVERIFIED.

Probing is gated by PCI IDs: `IF_DRAM_SMBUS`/`IF_MOBO_SMBUS` accept AMD 0x1022:0x790B and Intel 0x8086 SMBus devices 0x3A30, 0xA123, 0x2085, 0xA2A3, 0xA323, 0x06A3, 0xA3A3, 0x43A3, 0x7AA3, 0x7A23, 0x7F23 (MOBO additionally vendor 0 / 0xFFFF) (https://raw.githubusercontent.com/CalcProgrammer1/OpenRGB/master/pci_ids/pci_ids.h). `i2c_smbus.cpp` has no address blacklist; safety is per-detector.

Brick history (README WARNING, https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/README.md): "There have been issues in the past with certain hardware getting damaged/bricked... By installing and using OpenRGB you accept this risk." The stale wiki names the two incidents: MSI Mystic Light code "reportedly bricked the RGB on certain MSI boards", and "reports of bricked Gigabyte Aorus Z390 motherboards" from dumping SMBus address 0x68 (https://openrgb-wiki.readthedocs.io/en/latest/). DDR5: `DDR5DirectAccessor` writes `SPD_DDR5_MREG_VIRTUAL_PAGE` on page change and once more as a page-0 retry during probing (https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/SPDAccessor/DDR5DirectAccessor.cpp); issue #4934 (open, 2025-07 to 2026-08) collects "corrupt SPD on the DDR5 modules themselves... leading to boot failures" (ASUS PRIME B760M-K + XPG Lancer); no maintainer root-cause stated. ENE DRAM detection *writes* slot index/new address via 0x77 ("Remapping ENE SMBus RAM modules on 0x77"). Older G.Skill/Aura SPD-corruption threads are forum reports: UNVERIFIED.

**c) Port I/O / Super I/O / EC.** Yes: `super_io/` (Linux `/dev/port`; Windows 64-bit via PawnIO `LpcIO.bin`, "For 32-bit Windows... nonfunctional stub") used by `GigabyteSuperIORGBController` (ITE 8620/8688, only boards containing "X570 UD" or "Z390 DESIGNARE-CF") and `MSIRGBController` (Nuvoton NCT6795/6797, MSI DMI + board-code whitelist, e.g. 7B08). Laptop EC/WMI controllers (`wmi/`, Clevo, Faustus, ASUS TUF laptop, Lenovo) exist but were not inspected.

**d) Serial/network.** Serial: `LEDStripController`, `SkydimoSerialController`, `BlinkyTape`, `FanBus`, `Espurna`; `REGISTER_USB_SERIAL_DETECTOR(name, func, vid, pid)` exists. Network: Philips Hue (hueplusplus), Wiz, Nanoleaf, Yeelight, LIFX, Govee, Kasa, Elgato, E1.31, DDP, DMX.

**e) Vendor SDK/bridge.** NvAPI and AMD ADL (driver-shipped DLLs) for GPU I2C; PawnIO (third-party kernel driver). No vendor *service* (iCUE, Armoury Crate) is required; they are competitors for the device. Intel Arc on Windows: no path found (`i2c_intel_gpu.h` matches a Linux bus name); UNVERIFIED.

## 2. HID detection and protocols

Detection (https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/DetectionManager.h, .cpp): `hid_enumerate(0,0)` once, then each `HIDDeviceDetectorBlock {name, vid, pid, interface, usage_page, usage, bus, enabled_by_default}` is compared with `-1` wildcards; macro variants `REGISTER_HID_DETECTOR[_I|_IP|_IPU|_P|_PU|_B...]` and `_DISABLED`. Specific VID/PID detectors run before generic ones; first detector returning controllers wins. `hid_safe_mode` enumerates per VID/PID and skips generic detectors. Hotplug via hidapi callbacks.

Order: pre-detection hooks, I2C buses, I2C detectors, I2C DRAM (SPD JEDEC-gated), I2C PCI, HID, wrapped HID (Linux), USB serial, other.

Examples:

- **Corsair Lighting Node Pro/Core, Commander Pro** (0x1B1C: 0x0C0B/0x0C1A/0x0C10, plus LS100 0x0C1E, 1000D 0x1D00, LT100 0x0C23). 65-byte write (byte 0 report ID 0x00), 17-byte read, 15 ms timeout. Packet IDs: 0x02 firmware, 0x32 direct, 0x33 commit, 0x34 begin, 0x35 effect config, 0x37 reset, 0x38 port state (0x01 hardware, 0x02 software), 0x39 brightness (0-100). Direct: `[1]=0x32 [2]=channel [3]=start [4]=count [5]=plane(0=R,1=G,2=B) [6..]=count bytes`, 50 LEDs per chunk, three packets per chunk, then commit 0x33 with `[2]=0xFF`. Keep-alive thread: commit every ~5 s or device "reverts to rainbow mode" after 20 s (https://raw.githubusercontent.com/CalcProgrammer1/OpenRGB/master/Controllers/CorsairLightingNodeController/CorsairLightingNodeController.h).
- **NZXT Hue 2 / Smart Device V2 / RGB&Fan Controller** (0x1E71: 0x2001, 0x2002, 0x2005, 0x2006, 0x2009, 0x200B, 0x200D, 0x200E, 0x200F, 0x2010, 0x2011, 0x2012, 0x2019, 0x201B, 0x201F, 0x2020, 0x2021, 0x2022, Kraken Elite 0x3012; non-contiguous). 64-byte packets. `10 01` firmware, `20 03` device list (6 slots/channel at `0x0F+6*chan`, device IDs map to LED counts, e.g. 0x1D F360 = 24), `22 10|group` direct colors GRB from byte 4, 20 LEDs/packet, 2 groups (40 LEDs), then `22 A0` apply with `[2]=1<<channel`; `28 03` legacy effect, `2A 04` 2023 effect. No keep-alive, no brightness byte (https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/Controllers/NZXTHue2Controller/NZXTHue2Controller.cpp).
- **ASUS Aura USB** (0x0B05: 0x18F3, 0x1939, 0x19AF, 0x1AA6, 0x1BED; strips 0x1867/0x1872/0x18A3/0x18A5). 65 bytes, report ID 0xEC. 0x82 firmware, 0xB0 config table (reply `[1]==0x30`, 60 bytes from `[4]`, 6-byte records; ARGB/RGB counts at record+2/+3 per liquidctl), 0x35 effect, 0x36 effect color, 0x3F commit, 0x40 direct: `[2]=header | 0x80 apply | 0x10 8-bit overflow, [3]=start, [4]=count, [5..]=RGB`, 20 LEDs/packet (`LEDS_PER_PACKET 0x14`). liquidctl: direct "requires the continuous transmission of command codes" (https://raw.githubusercontent.com/CalcProgrammer1/OpenRGB/master/Controllers/AsusAuraUSBController/AsusAuraUSBController/AsusAuraUSBController.h; https://raw.githubusercontent.com/liquidctl/liquidctl/main/liquidctl/driver/aura_led.py).
- **Lian Li Uni Hub SL** (0x0CF2:0xA100, iface 1, 0xFF72/0xA1). Report ID 0xE0; 4 channels, 4 fans x 16 LEDs = 64 LEDs/channel. Per channel: activate `E0 10 32 (0x10*ch+fans)`, merge `E0 ... 0x33/0x34`, color `E0 (0x30+ch) [RBG x N]` ("The protocol uses R B G"), mode `E0 (0x10+ch) mode speed dir brightness`; 5 ms sleep per write; brightness is a 5-level enum (0x08 off .. 0x00 brightest). No keep-alive. Fan count is user-configured, not detected.

General shape: fixed-size reports (64/65), command byte at [1], channel bitmask or index, chunked per-LED payloads with an apply/commit, "Direct" implemented as a dummy mode ID (0xFFFF / 0xFF) that bypasses hardware effects; brightness is per-mode or a separate packet; some devices need keep-alive.

## 3. Data model (RGBController)

https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/RGBController/RGBControllerInterface.h and RGBController.h:
- Controller: `name, vendor, description, version, serial, location, configuration(JSON), display_name, type(device_type), flags, active_mode, vector<mode> modes, vector<zone> zones, vector<led> leds, vector<RGBColor> colors` (one flat color buffer; zones point into it). Virtuals: `DeviceUpdateLEDs, DeviceUpdateZoneLEDs(zone), DeviceUpdateSingleLED(led), DeviceUpdateMode, DeviceUpdateZoneMode, DeviceSaveMode, DeviceConfigureDevice/Zone`; `ResizeZone`, `AddSegment`, `SetupColors`.
- `device_type`: 22 values, MOTHERBOARD(0) .. MONITOR, UNKNOWN.
- `mode {name, value, flags, speed_min/max, brightness_min/max, colors_min/max, speed, brightness, direction, color_mode, colors}`; 12 `MODE_FLAG_*` bits (speed, 4 direction kinds, brightness, per-LED color, mode-specific color, random color, manual/automatic save, requires entire device); `MODE_COLORS_{NONE,PER_LED,MODE_SPECIFIC,RANDOM}`; 10 `MODE_DIRECTION_*` values.
- `zone {name, display_name, type, leds*, colors*, start_idx, leds_count, leds_min, leds_max, matrix_map{height,width,map}, segments, flags, modes, active_mode}`; 7 `ZONE_TYPE_*` (single, linear, matrix, loop and segmented variants). `led {name, value}`. `segment {name,type,start_idx,leds_count,matrix_map,flags}`.
- 9 `CONTROLLER_FLAG_*` (local/remote/virtual/hidden, reset-before-update, manually configurable name/device-specific).
- Semantics (https://raw.githubusercontent.com/CalcProgrammer1/OpenRGB/master/Documentation/Common-Modes.md, RGBControllerAPI.md): "Direct mode is a mode that allows setting individual LEDs to static colors" without fade or flash save; "Custom" may flicker/save; fixed zones have count==min==max; `UpdateLEDs()` sets a flag and a device thread performs the write.

## 4. Licensing facts

LICENSE is GPLv2 text (https://gitlab.com/CalcProgrammer1/OpenRGB/-/raw/master/LICENSE). Per-file SPDX varies: RGBController.h, i2c_smbus.cpp and the Corsair/ASUS/ENE/Gigabyte files read carry `GPL-2.0-or-later`, but LianLiUniHubSLController.h (2025) carries `GPL-2.0-only` (https://raw.githubusercontent.com/CalcProgrammer1/OpenRGB/master/Controllers/LianLiController/LianLiUniHubSLController/LianLiUniHubSLController.h); treat the effective license of any copied file as whatever its own header says, and the tree as a whole as GPLv2-compatible-only. Copying code (byte layouts expressed as code, tables, comments) into a non-GPL Rust project is a copyleft question; the protocol facts themselves (command bytes, VID/PIDs) are a separate legal question not settled here. liquidctl drivers are `GPL-3.0-or-later`, so copying from both into one codebase mixes GPLv2-or-later with GPLv3. Rust crates: `openrgb2` GPL-2.0 (SDK client), `hidapi` MIT, `mystic-light` MIT/Apache-2.0.

## 5. Blacklist / conflict detection

No conflicting-software detection exists in `DetectionManager.cpp`; no explicit address blacklist. The exclusion surface is: per-detector `enabled_by_default` persisted to settings JSON `detectors` (user-toggleable), `*_DISABLED` macros, `hid_safe_mode`, DMI/board whitelists (Gigabyte SMBus 21 boards, Gigabyte Super I/O 2 boards, MSI-RGB codes), PCI subsystem-vendor gates (ASUS/ASRock/Gigabyte), `IF_MOBO_SMBUS`/`IF_DRAM_SMBUS` PCI-ID gates, and `#ifdef ENABLE_UNTESTED_MYSTIC_LIGHT`. Runtime coexistence: PawnIO global SMBus mutex; Corsair device guard mutex. The old wiki says the SMBus Tools page is hidden by default after the Z390 incident.

## Rust ecosystem and liquidctl

- `openrgb2` 0.4.1 (2026-09, GPL-2.0, github.com/Achtuur/openrgb-rs2): async OpenRGB SDK *client*; needs the OpenRGB server. `openrgb` 0.1.2 (2022) is its abandoned predecessor (https://crates.io/api/v1/crates?q=openrgb).
- `mystic-light` 0.1.0 (2026-11-03, MIT/Apache, github.com/tweldy/mystic-light): per-LED MSI JARGB over HID; 10 downloads.
- Single-device/early crates: `hid-rgb-ctl` 0.2.6 (HID LampArray, Linux), `alienrgb` 0.1.0, `razer_driver_rs` 0.1.0 (2022), `liquidrust` 0.2.2 (one Corsair AIO), `nzxtcli` 0.1.1, `kraken_rs` 0.2.0 (2020), `zkraken-lib` 0.1.0. No Rust equivalent of OpenRGB's driver layer, SMBus access, or PawnIO binding was found. CoolerControl (`coolercontrold`, Rust, GPLv3, Linux-only) delegates to liquidctl via Python.
- liquidctl (https://github.com/liquidctl/liquidctl/blob/main/README.md) covers devices absent from OpenRGB's Controllers tree: Aquacomputer D5 Next/Farbwerk/Octo/Quadro, Corsair HX/RM i-series PSUs, NZXT E-series PSUs, NZXT Grid+ V3, ASUS Ryujin II/III (OpenRGB has only `AsusAuraRyuoAIO`), MSI MPG Coreliquid K360. liquidctl marks Corsair Hydro v2/GTX/Pro, EVGA CLC, Kraken X40-X61 as "Z" = requires replacing the Windows driver (WinUSB via Zadig), and warns that doing so on a HID device breaks it.
